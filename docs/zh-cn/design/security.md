# 安全责任与边界

> 相关文档: [index.md](index.md) (整体设计) · [plugins.md](plugins.md) (插件系统) ·
> [roadmap.md](roadmap.md) (实施状态清单)
>
> 本文说明 agentxx 的权限系统**能约束什么、不能约束什么**，以及已知的覆盖边界。
> 安全相关改动的评审约定见 `agent/lib/AGENTS.md`。

## 1. 三条基本判断

### 1.1 权限系统约束的是"模型经工具发起的运行期动作"

权限中间件（`agent/lib/src/middlewares/permission.cpp`）在工具调用真正执行前判定目标：

- 只对**模型产生的工具调用**生效（`ToolcallWrapNode` 的调用路径）；
- 判定对象是工具声明的目标参数（路径 / 文本），不是进程行为；
- 人类用户自己在终端里做的操作、宿主代码直接调用的内部路径、widget/插件的直接调用都不经过它。

因此权限系统是**人机之间的确认与提醒机制**，不是进程隔离机制。

### 1.2 插件与宿主同权，不受权限系统约束

插件是以动态库形式加载进**同一进程**的原生 C++ 代码：

- 加载插件等于信任该插件的全部代码，它与 agentxx 主体拥有同样的文件、网络和进程权限；
- 插件可以自行读取任何文件、发起任何网络连接、启动任何进程，权限中间件无法阻止它；
- 插件为自身工具注册的权限声明（`agentxx.agent.permission` 接口表）只是"哪些参数是受约束目标"的**约定**：声明后该工具的调用会走权限判定，未声明的工具直接放行；
- 因此插件路径**只能**来自用户显式配置（`plugin.list[].path`），不要加载来路不明的动态库。

### 1.3 门禁判定不是隔离，真正的隔离只能由沙箱或系统边界提供

路径规则、workspace 隔离、三态路径检查都作用于"工具调用目标字符串"，属于**判定正确性**措施：

- 它们无法限制进程实际能碰到的资源（例如工具内部的间接访问、子进程自身的行为）；
- 强制隔离需要操作系统边界（Linux bubblewrap / Landlock、macOS Seatbelt 等）。这类可选执行后端尚未实现，见 [roadmap.md](roadmap.md) 的"未来计划"。

**不要把本项目的权限规则当作安全边界来部署。** 需要在不可信内容或多用户环境下运行时，
应在外层使用容器、独立系统账号或虚拟机。

## 2. 权限系统当前覆盖范围

### 2.1 判定顺序

单目标判定（`PermissionMiddlewareHandle::explainTarget`）依次为：

1. **worktree 会话隔离**：绑定了 worktree 的会话，对主检出子树的写操作直接拒绝（读不受限）；
2. **配置显式拒绝**（`permission.blacklist` / `permissionDenyPaths`）：无论是否完全授权，始终拒绝且不询问；
3. **完全授权**（用户在询问卡片里勾选，或客户端 `WireSetFullAuth` 切换）：允许；
4. **规则表命中**：最长前缀匹配（`permission.whitelist`、记住的选择、工作目录规则）；
5. **兜底**：`noRuleOperator`（由 `permission.mode` 决定：`ask`/`all_ask` → 询问，`pass` → 允许，`deny` → 拒绝）。

`permission.mode` 的默认值 `ask` 表示"当前会话工作目录内允许读写，其他路径询问用户"。

**判定理由**（`PermissionReason`）：每一步都同时给出理由（工作区隔离 / 配置拒绝 / 完全授权 /
命中规则 / 未命中按默认 / 未解析）以及命中的规则与目标，日志与拒绝文本共用同一份说明
（拒绝时工具结果形如 `[Permission denied] blocked by configuration deny rule [target: ...]`），
避免"同一路径在两处得到不同解释"。

**执行前目标复验**（`service.permission.reverify`）：判定阶段按 (工具名, `tool_call_id`)
记录已批准的目标集合，工具执行体启动前用最终参数按同一口径重新解析并比对，不一致即拒绝
执行（`[Permission denied] permission target changed between check and execution (...)`）。
纯校验、不重复询问用户，用来保证"批准的对象 = 执行的对象"。

### 2.2 已知覆盖边界

| 边界 | 现状 | 说明 |
|---|---|---|
| 符号链接 | 未解析链接目标 | 判定基于词法规范化路径；允许目录内的链接指向被拒目录时，实际访问会跟随链接。代码中已有 TODO，见 roadmap "未来计划"。 |
| 命令执行 | 无路径目标声明 | `agentxx_execute_bash_command` / `agentxx_execute_windows_command` 不做权限询问（命令无法可靠地映射到单一路径目标），命令能读写、能联网、能启动任意进程。 |
| 网络出网 | 无统一策略 | 没有出网分类与内网阻断；插件（websearch、MCP、RAG）按自身配置连接目标地址。配置中的 URL 应视为可信输入。 |
| 设备采集 | 无目标声明 | 截屏 / 桌面控制类插件按调用即执行。 |
| 附件 | 不主动抓取 URL | 宿主只读取**本地路径**附件（受大小上限约束）；`http(s)://` 形式的 URL 原样交给模型 provider，由 provider 侧抓取。 |
| 插件 | 无任何限制 | 见 §1.2。 |

### 2.3 工具权限声明现状

声明权限目标的工具（走权限判定）：

- `agentxx_filesystem` 插件的 `read` / `list` / `write` / `edit`（路径目标，读写作用域）。

未声明权限的工具（直接放行）：

- `agentxx_execute_command`（命令执行，见上表）；
- `agentxx_websearch`、`agentxx_rag_search`（文本目标未声明）；
- 截屏 / 桌面控制 / 系统监控等设备类插件；
- 其他第三方插件工具。

跨边界的批量查询：带模式或前缀参数的插件工具（glob / grep / list 等）可用
`agentxx.agent.permission` 的 `check_paths` 对**枚举出的实际路径**逐项做三态查询
（`DENY` / `ALLOW` / `ASK`），只保留明确允许或已获批准的路径——这一步避免 `**` 之类
的模式绕过多层目录的拒绝规则。

## 3. 安全相关配置的语义

| 配置项 | 位置 | 语义 |
|---|---|---|
| `permission.mode` | YAML | 未命中规则时的默认动作（ask / all_ask / pass / deny）。 |
| `permission.whitelist.list` | YAML | 始终放行的路径（最长前缀匹配，支持 `*`）。 |
| `permission.blacklist.list` | YAML | 始终拒绝的路径；**优先于完全授权**，用于"绝不触碰"的目录。 |
| `worktree.enable` | YAML | 开启后模型可创建 git worktree；绑定后写操作被限制在该 worktree 子树内。 |
| `plugin.list[].path` | YAML | 插件动态库路径：**加载即信任**，只配置自己验证过的插件。 |
| 完全授权 | 运行时（内存） | 询问卡片勾选或客户端切换；进程退出即失效，不持久化。 |
| 记住的选择 | 运行时（内存） | 同一次运行内同目标不再询问；不写盘，重启后重新询问。 |

工作目录（`work_dir`）同时是权限判定的默认放行范围和相对路径解析基准，因此它决定
"哪些路径属于本会话的正常工作区"。

## 4. 使用建议

1. 在受限账号或容器中运行 agent，把它当作"有本机权限的开发者助手"而不是沙箱内的进程。
2. 用 `permission.blacklist` 明确排除凭据目录（`~/.ssh`、`~/.aws`、云厂商配置目录等）。
3. 只加载自己编译或审核过的插件；`plugin.list` 指向的路径要固定在受控目录。
4. 长任务使用 worktree 模式，让多会话的写操作彼此隔离。
5. 不要在提示词、上下文文件或技能里写入长期有效的密钥：它们会进入模型请求。
6. 出网能力由被调用的工具和插件决定；如部署环境需要限制，请在网络层（代理、防火墙、容器网络策略）处理。
