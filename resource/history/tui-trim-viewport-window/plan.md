# 方案: 本地展示消息的保留窗口

## 背景

客户端 (TUI) 的展示历史副本原先只在"滚动位置在底部"时才清理头部消息:

```text
清理条数 = min(条数 - kLocalMessageLimit, 视口顶行下标)
条件     = 条数 > kLocalMessageLimit 且 吸附底部
```

结果是用户往上翻看历史期间完全不清理: 期间新到的消息全留在内存里, 列表长度跟着会话
一直涨 (服务端的内存窗口有上限, 客户端这份没有)。而实际上"视口上方的更早消息"随时
可以删 —— 它们在服务端展示历史里仍然存在, 上滚到窗口顶部时按页拉回。

## 方案

保留窗口取两个条件中较大的那个:

1. 末尾 `kLocalMessageLimit` (100) 条 —— 跟随最新内容时的常驻量;
2. 视口顶行及其后的全部消息 + 视口上方 `kLocalMessageViewportMargin` (3) 条 ——
   用户正在看的内容, 以及往上滑一点还能看到的几条。

```text
visible      = min(视口顶行所在消息下标, 条数)
fromViewport = 条数 - visible
keep         = max(kLocalMessageLimit, fromViewport + min(visible, margin))
清理条数     = 条数 > keep ? 条数 - keep : 0
```

- 底部的场景与旧行为一致 (视口就在末尾 -> 保留末尾 100 条);
- 上滚场景: 视口在倒数第 N 条时保留末尾 N + 3 条, 更旧的清掉;
- 视口顶行在第 0 条 (整段内容都在屏幕上) 时 `keep == 条数`, 清理 0 条;
- 兜底再夹一次 `清理条数 <= visible - margin`, 保证视口内的消息与上方 3 条不被删。

为什么取 max 而不是"只要上滚就按视口算": 用户上滚得不深时 (视口距末尾不足 100 条)
仍按 100 条常驻, 不至于每来一条新消息就删一条头部消息。

## 判定在哪执行

"视口顶行是哪一条"只有 UI 线程独占的消息列表组件知道, 所以判定与执行仍在
`TUIClientAgentIO::applyLocalTrimCheck` (UI 线程帧首动作)。client 线程只在追加消息后
投递一次检查 (原子去重)。

窗口记账不变: 删除头部消息后 `HistoryWindow::noteTrimmedHead(dropped)` 把已加载窗口
起点右移, `hasMore()` 重新为真, 上滚到窗口顶部时再按页拉回这一段。

## 触发点

原先只有本地行 (用户输入回显 / 瞬态提示) 会投递检查, agent 下发的历史行
(`insert_message`) 与断线增量补拉都不投递 —— 长轮次里客户端列表会先涨到很远才清理。
本次一并补上这两个触发点 (都是"条数超过上限才投递", 由原子去重合并到一帧一次)。

## 边界

- 未启动界面 / 无消息列表组件 (基准端点): `trimSafeHeadCount` 读不到锚点 (0),
  判定结果为 0, 不清理;
- 锚点落在流式子项 (下标 >= 消息数) 时按消息数算, 等于"消息全都在视口上方",
  即按末尾 100 条保留;
- 清理动作排队期间列表被整体替换 (切换会话/尾窗同步) 或变短: 锁内按最新条数重算,
  重新算出的条数为 0 时不做任何事;
- 首次布局前锚点为 0: 不清理, 等第一帧布局后有锚点再判。

## 验证

- 判定函数: 独立小程序 (只含 `message_window.h`) 穷举 `条数 0..400 × 视口下标 0..条数`,
  校验三条不变量: 不删视口内消息、清理后条数 >= 100、清理条数不超过条数; 逐条用例
  覆盖底部/上滚/视口在顶部/锚点越界;
- 项目内测试 (`tui_model` 判定用例、`tui_scroll` 场景 D) 已按新规则更新并通过;
  全量测试 42721 条断言全部通过 (见 work.md)。
