# 真实 TUI 长上下文 5 档 GB 级实测 (20M / 100M / 200M / 1G / 2G)

- 状态: 已完成 (代码 + 实测 + 报告 + 文档)
- 主题: `resource_tui_longctx` 场景的采样点从 4 档 token 改成 5 档累计内容字节, 实测内存是否
  随累计内容增长, 并定位内存占用根源
- 代码: `agent/benchmark/bench_resource_real.cpp` (`benchResourceTuiLongCtx`)
- 文档: [plan.md](plan.md) (设计) · [work.md](work.md) (实施记录) · [report.md](report.md) (实测报告)
- 长期结论: [docs/zh-cn/design/benchmark.md 第 20 节](/docs/zh-cn/design/benchmark.md)

## 关键决策

1. 采样点单位 = **累计内容字节** (旧的是 token), 名字带 `b` 后缀 (`ctx20mb`/`ctx2gb`), 避免与
   旧批次 `ctx2m` (2M token) 混淆。
2. 累计拆两条路径: 真实轮次 (默认先累积 2 MB) + 展示历史注入 (`Session::appendViewMessage`,
   同一条内存/落库路径)。真实轮次地板 8.6 KB/980 ms 一轮, 单条 8 KB 跑到 2 GB 要 24 万轮
   (≈65 小时), 不具可行性; 反过来放大单条消息会让 400 条窗口线性涨到 100 MB。
3. 采样点额外记录**会话库磁盘字节**与"内存里的内容"字节, 用来验证"转存到磁盘、内存只留窗口"。
4. 另做两条对照 (关会话库 / 关插件), 量化这两块对 RSS 的贡献。

## 结论

1. **内存不随会话历史增长**: 累计内容 20 MB → 2 GB (×102)、会话库 27.9 MB → 2.14 GB (×78),
   内存里的内容恒定 **3.6 MB** (占 2 GB 的 0.18%), RSS 两次运行都在 **47~55 MB**;
   20 MB → 2 GB 只涨 **+7.8 MB (运行 A) / +4.9 MB (运行 B)**, 且不是单调。
2. **上限只由三处决定** (与累计内容无关): 服务端展示尾窗 400 条 (实测 303 条 / 2.47 MB)、
   客户端窗口 100 条 (0.81 MB)、LLM 上下文 75% 压缩 (87 K → 96 K token / 0.34 → 0.37 MB)。
3. **"自动转存"省了多少有实测**: 关掉会话库后展示历史不再淘汰, 同样 20 MB 内容
   RSS 47.09 → **65.27 MB** (+19.0 MB, 内存里 21.9 MB 正文), 而且会随累计内容 1:1 放大。
4. **47 MB 的构成**: 数据 3.6 MB + 进程底座 ≈18 MB (exe/系统库/mock 服务/FTXUI/
   AgentHost+5 插件, 其中插件 5.0 MB) + 每轮临时缓冲堆高水位 ≈25 MB (峰值在压缩轮)。
5. **GB 级时 RSS 在 50 MB 上方 3~5 MB**, 来自活上下文变大后的临时块、sqlite 页缓存/WAL 与
   批量写入留下的空闲页 (Windows 侧没有堆归还)。要再压, 应先补"堆归还"而不是动数据结构。
