- 日期: 2026-11-28
- 构建: Windows 10.0 (build 26200) / 12 核 / 53 GB / MSVC 19.51 / **Release**
  (`agent/build/windows-release/exec/agentxx_benchmark.exe`, 主仓 `b04729e3` + 本次工作区改动)
- 机器负载: 两次运行期间 CPU 占用 1~3% (空闲), 同机另有 3 个 agentxx 进程常驻 (与本进程无关)
- 原始报告 (两次运行, 参数相同):

1. **内存不随会话历史增长**: 累计内容 ×102 (20 MB → 2 GB)、会话库 ×78, 内存里的内容恒定在
   **3.6 MB (占 2 GB 的 0.18%)**; 两次运行的 RSS 都在 **47 ~ 55 MB** 区间, 20 MB → 2 GB 的
   差异只有 **+4.9 MB (B) / +7.8 MB (A)**, 与 2,161 MB 的会话库增长无关。
2. **基本满足 "<50 MB" 的预期, GB 级时略高**: 20 MB ~ 200 MB 三档 47.1~50.8 MB,
   1 GB / 2 GB 档 49.9~54.8 MB (A) 与 52.8~53.1 MB (B) —— 约 50~55 MB。多出来的部分**不是
   消息正文** (正文全在库里, 内存里只有 3.6 MB), 而是进程底座 + 每轮临时缓冲的堆高水位
   (见第 4 节)。
3. **内存上限只由三处决定** (与"累计内容"无关):
   - 服务端展示历史尾窗 `session.view_window_messages` = 400 条 (实测稳定在 303 条 / 2.47 MB);
   - 客户端本地窗口 `kLocalMessageLimit` = 100 条 (尾窗重同步后 0.81 MB);
   - LLM 上下文达模型上限 75% 自动压缩 (实测 87 K → 96 K token / 0.34 → 0.37 MB)。
4. **会话库是"转存"的落点**: 2 GB 内容 → 2.14 GB 库 (1.07 倍)。关掉会话库后展示历史不再
   淘汰, 同样 20 MB 内容 RSS 从 47.09 MB 涨到 **65.27 MB** (内存里 21.9 MB 正文) ——
   这条对照直接量化了"窗口 + 会话库"省下的量 (≈19 MB, 且会随累计内容 1:1 放大)。
5. **真正的常驻大头不是数据**: 47 MB 里只有 3.6 MB 是消息/上下文数据; ≈18 MB 是进程底座
   (exe + 系统库 + mock LLM 服务 + FTXUI 界面 + AgentHost/插件); ≈25 MB 是每轮请求/落盘
   临时缓冲留下的堆高水位 (峰值出现在压缩轮)。

## 2. 场景与测量方式

| 项 | 值 |
|---|---|
| 装配 | `AgentHost` + 5 基准插件 + `Channel` + `SessionServerAgentIO(tail=100)` + 真实 FTXUI 界面线程 + 会话库开 |
| 每轮输入 | 8192 字节用户消息 (估算 2052 token) |
| 每轮回复 | 600 字节 (155 token), 48 个 SSE 帧, 帧间 1 ms |
| 模型上限 | 300000 token → 75% (225000) 触发自动压缩 |
| 采样点 | **累计内容字节** 20M / 100M / 200M / 1G / 2G (K/M/G = 1024 进制) |
| 累积方式 | `history` 模式: 真实轮次先累积 2 MB, 其余按采样点差额注入展示历史 (见 2.1) |
| 测量规则 | 采样点不做堆归还 (`malloc_trim`/`_heapmin`), 否则会抹平稳态; 采样均在"轮次刚结束、会话空闲" |

### 2.1 为什么"累计内容"要拆成真实轮次 + 注入历史

真实轮次有时间地板: 本次实测 **8.6 KB/轮、约 930~1090 ms/轮** (活上下文 ~225 K token 时),
单条 8 KB 消息跑到 2 GB 需要 **24 万轮 ≈ 65 小时**, 不具可行性。反过来把单条消息放大到
256 KB, 400 条窗口就是 100 MB (窗口按条数淘汰), 也不是"内存只保留一部分"的场景。

所以默认走 `history` 模式: 真实轮次累积到 `AGENTXX_TUI_CTX_REAL_BYTES` (默认 2 MB, 本次
240 轮), 之后每个采样点把差额**注入展示历史** —— 直接调会话的写入入口
`Session::appendViewMessage` (与真实轮次同一条内存/落库路径, 每 1024 条 flush 一次),
注入后让客户端重新尾窗同步一次 (`historyTail=100`)。两条路径的差别只在"消息从哪来",
下游的窗口淘汰/落库/客户端窗口用同一份代码。

已否决的提速办法 (记录以免重走): 一轮注入多条 `next-step` 消息。实测没赶上本轮 modelcall
边界的输入会被 `rolloverLeftoverNextStepInputs` 合并成一条 `source=event:pending-rollover`
的 event 输入交给下一轮 —— 展示行变成 57 KB 的合并行 (400 条窗口 12~15 MB), 吞吐还只有
67 ms/条 (2156 ms/批), 2 GB 仍要 4.9 小时。

### 2.2 注入吞吐

| 档位 | 注入量 | 耗时 (运行 A) | 速率 |
|---|---|---|---|
| 20M | 18.0 MB (2,301 条) | 2.9 s | 6.2 MB/s |
| 100M | 80.0 MB (10,240 条) | 13.1 s | 6.1 MB/s |
| 200M | 100.0 MB (12,800 条) | 17.1 s | 5.8 MB/s |
| 1G | 824.0 MB (105,471 条) | 134.8 s | 6.1 MB/s |

每条 ≈1.27 ms (建 `ViewMessage` + 窗口淘汰 + 批量落库), 即"转存"本身的成本; 2 GB 全部
转存约 5.5 分钟。

### 3.4 对照实验 (都在 20 MB 采样点, 其余参数相同, 各跑一次)

| 变体 | 展示窗口 | 内存内容 | RSS | 私有 | 峰值 RSS | 会话库 |
|---|---|---|---|---|---|---|
| 基线 (库开 + 5 插件) | 303 条 / 2.47 MB | 3.61 MB | 47.09 MB | 30.96 MB | 55.22 MB | 27.9 MB |
| 会话库**关** | 3,028 条 / 21.2 MB | 21.90 MB | 65.27 MB | 48.18 MB | 65.98 MB | 0 |
| 插件**关** (5 → 0) | 303 条 / 2.47 MB | 3.61 MB | 41.27 MB | 25.51 MB | 50.89 MB | 27.9 MB |

- **会话库关 → RSS +18.98 MB**: 没有库就没有淘汰 (`viewWindowCap = 0`), 20 MB 内容的
  3,028 条消息全留在内存里 (21.2 MB)。这就是"自动转存"省下的部分, 且随累计内容**线性**放大
  (2 GB 时会多出 ~2 GB)。
- **5 个基准插件 → 5.02 MB RSS / 4.65 MB 私有**: 插件动态库 + 工具注册表 + 提示词 +
  各自运行期状态; 与累计内容无关。

## 4. 内存占用根源

### 4.1 47 MB 拆成三块

| 部分 | 大小 | 来源 | 与累计内容的关系 |
|---|---|---|---|
| 数据本体 (逻辑内存) | 3.6 MB | 展示尾窗 2.47 + LLM 上下文 0.37 + 客户端窗口 0.81 | **无关** (受窗口条数 / token 上限约束) |
| 进程底座 | ≈18 MB | exe + 系统/第三方 DLL + mock LLM 服务 (8.98) + 界面线程 (2.46) + `AgentHost`/agent init/5 插件 (6.01) | 无关 |
| 每轮临时缓冲的堆高水位 | ≈25 MB | 每轮把整段上下文序列化成请求体 (活上下文 ~900 KB 正文 → 1 MB 级 JSON) + 落盘 JSON (同量级), 两者同轮共存; 峰值出现在压缩轮 | **间接**: 只跟"活上下文多大"有关 |

- 私有 (commit) 37.23 MB 里也只有 3.65 MB 是数据, 其余是 CRT 堆 arena、线程栈、
  sqlite page cache / WAL 映射、插件私页与上面的临时高水位。
- 直接证据: 关会话库 (数据本体 3.6 → 21.9 MB) → RSS 同步 +18.98 MB (≈1:1);
  关 5 个插件 (数据本体不变) → RSS −5.02 MB。**RSS 跟着"内存里放了多少东西"走,
  不跟着"历史有多长"走。**

### 4.2 20 MB → 2 GB 为什么还涨了 5~8 MB

1. **活上下文随轮次上移** (87 K → 96 K token): 每轮请求体/落盘 JSON 的临时块同比变大,
   压缩周期落点不同会带来 ±1~2 MB 差异;
2. **会话库变大后的页缓存 / WAL**: 库从 27.9 MB 涨到 2.14 GB, WAL 固定在 ~4.6 MB
   (autocheckpoint 1000 页), page cache 默认 2 MB —— 有上限, 但新 WAL 页仍在映射里时
   RSS 会多几 MB;
3. **批量注入的堆高水位**: 每批 1024 条 (8.4 MB 消息 + 同量级落库 JSON) 分配/释放,
   CRT 堆保留的空闲页不会归还 (Windows 侧项目里没有 `_heapmin` /
   `SetProcessWorkingSetSize` 的定期归还), 表现为随注入条数缓慢抬升的碎片;
4. 两次运行在同一档位最多差 3.5 MB, 说明这项波动和"内容多少"不是线性关系
   (运行 A 的末档 +4.93 MB 在运行 B 里只有 +0.30 MB)。

### 4.3 峰值 55~58 MB 从哪来

峰值出现在**真实轮次阶段的压缩轮**: 压缩要一次性拼出完整上下文请求 (≈900 KB 正文 +
JSON/拷贝 + 子代理上下文), 同时在轮末把 LLM 上下文与展示历史整表落盘。两次运行的
峰值 55.22 / 57.00 MB 都产生在这一阶段, 与"历史多大"无关 (5 档共用同一个峰值)。

### 4.4 一句话公式

> 常驻内存 ≈ 进程底座 (~18 MB) + 插件 (5 MB) + 每轮临时缓冲高水位 (~20~25 MB)
>  + 展示尾窗 (≤400 条 × 单条字节) + 客户端窗口 (100 条 × 单条字节)
>  + LLM 上下文 (≤ 模型上限 75%)
>
> **与"累计内容"无关**: 累计内容全部在会话库里 (本次 2.14 GB), 内存里恒为 3.6 MB / 0.18%。

上一批 (benchmark.md 第 19 节) 用 100K/200K/1M/2M **token** 累计输入做到 907 轮, 结论是

| 项 | 上一批 (2M token ≈ 8 MB 内容) | 本批 (2 GB 内容) |
|---|---|---|
| 展示窗口 | 332 条 (总 2,732 条) | 303 条 (总 262,620 条) |
| 活上下文 | 19 K ~ 222 K token (压缩周期) | 87 K ~ 96 K token |

## 7. 遗留与建议

1. **没有量"重启后冷加载 2 GB 会话"**: 需要重建 agent + 插件, 本次未做。按现有窗口上限
   推断 (`loadSession` 只取尾窗 400 条 + 压缩后的 LLM 上下文), 冷加载常驻应与 3.6 MB
   同量级, 但需要实测确认。
2. **展示窗口按条数、不按字节**: 单条消息越大, 400 条窗口的常驻越大 (本次 8 KB × 303 ≈
   2.5 MB)。若要支持"单条几十 MB 的粘贴", 需要给窗口补字节上限 (本次未改代码)。
3. **Windows 侧没有堆归还**: 批量写入/压缩轮留下的空闲页会一直算在 RSS 里 (Linux 有
   `malloc_trim`); 是否加 `_heapmin` / `SetProcessWorkingSetSize` 需要单独评估
   (会影响每轮耗时)。这是 GB 级历史下 RSS 仍在 50 MB 上方 3~5 MB 的主要可回收项。
