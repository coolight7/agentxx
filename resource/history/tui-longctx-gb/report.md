## 2. 场景与测量方式

| 项 | 值 |
|---|---|
| 装配 | `AgentHost` + 5 基准插件 + `Channel` + `SessionServerAgentIO(tail=100)` + 真实 FTXUI 界面线程 + 会话库开 |
| 每轮输入 | 8192 字节用户消息 (估算 2052 token) |
| 每轮回复 | 600 字节 (155 token), 48 个 SSE 帧, 帧间 1 ms |
| 模型上限 | 300000 token → 75% (225000) 触发自动压缩 |
| 采样点 | **累计内容字节** 20M / 100M / 200M / 1G / 2G (K/M/G = 1024 进制) |
| 累积方式 | `history` 模式: 真实轮次先累积 2 MB, 其余按采样点差额注入展示历史 (见 2.1) |
| 测量规则 | 采样点不做堆归还 (`malloc_trim`/`_heapmin`), 否则会抹平稳态; 采样均在"轮次刚结束、会话空闲" |

### 2.1 为什么"累计内容"要拆成真实轮次 + 注入历史

真实轮次有时间地板: 本次实测 **8.6 KB/轮、约 930~1090 ms/轮** (活上下文 ~225 K token 时),
单条 8 KB 消息跑到 2 GB 需要 **24 万轮 ≈ 65 小时**, 不具可行性。反过来把单条消息放大到
256 KB, 400 条窗口就是 100 MB (窗口按条数淘汰), 也不是"内存只保留一部分"的场景。

所以默认走 `history` 模式: 真实轮次累积到 `AGENTXX_TUI_CTX_REAL_BYTES` (默认 2 MB, 本次
240 轮), 之后每个采样点把差额**注入展示历史** —— 直接调会话的写入入口
`Session::appendViewMessage` (与真实轮次同一条内存/落库路径, 每 1024 条 flush 一次),
注入后让客户端重新尾窗同步一次 (`historyTail=100`)。两条路径的差别只在"消息从哪来",
下游的窗口淘汰/落库/客户端窗口用同一份代码。

已否决的提速办法 (记录以免重走): 一轮注入多条 `next-step` 消息。实测没赶上本轮 modelcall
边界的输入会被 `rolloverLeftoverNextStepInputs` 合并成一条 `source=event:pending-rollover`
的 event 输入交给下一轮 —— 展示行变成 57 KB 的合并行 (400 条窗口 12~15 MB), 吞吐还只有
67 ms/条 (2156 ms/批), 2 GB 仍要 4.9 小时。

## 4. 内存占用根源

### 4.1 49 MB 的实测分解 (Windows 常驻内存按区域归属)

2026-11-28 给基准程序补了 Windows 侧的常驻分解 (`bench_mem_probe.h`: `VirtualQueryEx`
枚举已提交区域 + `QueryWorkingSetEx` 逐页取驻留位, 等价 Linux 的 `smaps`; 堆明细用
`HeapSummary`), 于是 20 MB 档的 49 MB 可以按"区域属于谁"直接量出来, 不用再推:

| 归属 | 常驻 (RSS) | 占 RSS | 映像大小 | 说明 |
|---|---|---|---|---|
| 基准程序自身 `agentxx_benchmark.exe` | **10.17 MB** | 20.7% | 23.05 MB | 静态链接了 libagentxx/工具库/FTXUI/sqlite/OpenSSL/curl, 执行到哪页哪页常驻 |
| 系统 DLL | **10.48 MB** | 21.4% | 71.4 MB | ntdll 1.87 / KernelBase 1.12 / icu 0.92 / ucrtbase 0.64 / rpcrt4 0.53 / dnsapi 0.45 / shell32 0.45 / kernel32 0.40 … (220 段) |
| 5 个插件 DLL | **2.39 MB** | 4.9% | 8.80 MB | filesystem 0.69 / execute_command 0.56 / planning 0.47 / websearch 0.37 / system 0.30 |
| 项目库映射 | 0.51 MB | 1.0% | 0.92 MB | 静态链剩余的几个 DLL 映射 |
| **私有匿名 (CRT 堆)** | **25.18 MB** | 51.4% | 29.99 MB | 堆活对象 13.61 MB, 已提交 32.77 MB, 预留 50.77 MB |
| 页文件映射 (shm) | 0.25 MB | 0.5% | 3.23 MB | 20 段 |
| 数据文件映射 | 0.03 MB | 0.1% | 0.03 MB | 1 段 |
| 线程栈 | ≈0 MB | 0% | 0.36 MB | 31 个线程栈基本不在工作集里 (换出到页面文件) |
| 合计 | 49.01 MB | — | — | 与 RSS 49.04 MB 一致 (差 0.03 = 采样时刻抖动) |

**结论: 除数据外的那 25 MB 不是一个东西, 而是两半** ——

1. **代码页 23.6 MB (48%)**: 程序自己是 10.2 MB 的机器码/只读数据 (映像 23 MB,
   只有执行到的页在), 系统 DLL 10.5 MB, 插件 DLL 2.4 MB。这部分是"程序本体的固定成本",
   跟会话长短、内容多少完全无关, 也不随累计内容增长。
2. **CRT 堆 25.2 MB (51%)**: 活对象只有 13.6 MB, 其余 ~11.6 MB 常驻页是
   **已释放但留在堆里的空闲块** (堆已提交 32.8 MB − 活对象 13.6 MB = 19.2 MB 空闲,
   其中一部分被换出)。用独立探针验证: 分配 12.8 MB 再释放 90% 后 `HeapSummary.cbCommitted`
   一个字节都不降 —— Windows CRT 堆不向系统归还空闲页 (项目里也没有 `_heapmin` 定期归还),
   所以 RSS 停在"历史峰值", 而不是"当前活数据"。

活对象 13.6 MB 里能对上数据的只有 **3.9 MB** (展示尾窗 2.59 + 客户端窗口 0.85 +
LLM 上下文 0.35 + 索引/配置/工具 schema 0.12), 剩下 ≈ 9.7 MB 是运行时对象。已测到的边界:
5 个插件合计 5.8 MB (插件全关对照 47.09 → 41.27 MB)、客户端 100 条消息 0.85 MB、
sqlite 默认页缓存 2 MB/连接。

### 4.2 20 MB → 2 GB 为什么还涨了 5~8 MB

1. **活上下文随轮次上移** (87 K → 96 K token): 每轮请求体/落盘 JSON 的临时块同比变大,
   压缩周期落点不同会带来 ±1~2 MB 差异;
2. **会话库变大后的页缓存 / WAL**: 库从 27.9 MB 涨到 2.14 GB, WAL 固定在 ~4.6 MB
   (autocheckpoint 1000 页), page cache 默认 2 MB —— 有上限, 但新 WAL 页仍在映射里时
   RSS 会多几 MB;
3. **批量注入的堆高水位**: 每批 1024 条 (8.4 MB 消息 + 同量级落库 JSON) 分配/释放,
   CRT 堆保留的空闲页不会归还 (§4.1 的独立探针: 分配 12.8 MB 后再释放 90%,
   `HeapSummary.cbCommitted` 一字节不降), 所以 RSS 停在历史峰值而不是当前活数据;
4. 两次运行在同一档位最多差 3.5 MB, 说明这项波动和"内容多少"不是线性关系
   (运行 A 的末档 +4.93 MB 在运行 B 里只有 +0.30 MB)。

### 4.3 峰值 55~58 MB 从哪来

峰值出现在**真实轮次阶段的压缩轮**: 压缩要一次性拼出完整上下文请求 (≈900 KB 正文 +
JSON/拷贝 + 子代理上下文), 同时在轮末把 LLM 上下文与展示历史整表落盘。两次运行的
峰值 55.22 / 57.00 MB 都产生在这一阶段, 与"历史多大"无关 (5 档共用同一个峰值)。

### 4.4 一句话公式

> 常驻内存 ≈ 代码页 (49 MB 里 23.6 MB: exe 10.2 + 系统 DLL 10.5 + 插件 2.4)
>  + CRT 堆常驻 (25.2 MB: 活对象 13.6, 其中数据 3.9; 空闲/未归还 ~11.6)
>  + 页文件映射/数据文件 (0.3)
>
> 其中唯一跟会话内容有关的是"活对象里的数据" (≤ 展示尾窗 400 条 + 客户端窗口 100 条
>  + LLM 上下文 ≤ 模型上限 75%, 本次 3.9 MB)。代码页与堆的空闲块都是**固定成本**:
> 前者只取决于编译产物与按需加载的 DLL, 后者取决于**历史峰值**(堆不归还), 两者都不随
> 累计内容增长 —— 这就是 20 MB 与 2 GB 两档 RSS 只差 5~8 MB 的原因。
>
> **与"累计内容"无关**: 累计内容全部在会话库里 (本次 2.14 GB), 内存里恒为 3.6 MB / 0.18%。

| 会话库 | 未量 | 2.14 GB |
| RSS | 48.1 ~ 55.6 MB | 47.1 ~ 54.8 MB (A) / 48.1 ~ 53.1 MB (B) |
| 峰值 RSS | 63.6 MB | 55.2 / 58.0 MB |

两批 RSS 量级一致 (47~56 MB), 说明 6 位数的累计内容增长**没有**在常驻内存上留下痕迹;
本批峰值更低是因为真实轮次只跑了 240 轮 (没有让上下文在 225 K token 顶部长时间停留)。

## 7. 遗留与建议

1. **没有量"重启后冷加载 2 GB 会话"**: 需要重建 agent + 插件, 本次未做。按现有窗口上限
   推断 (`loadSession` 只取尾窗 400 条 + 压缩后的 LLM 上下文), 冷加载常驻应与 3.6 MB
   同量级, 但需要实测确认。
2. **展示窗口按条数、不按字节**: 单条消息越大, 400 条窗口的常驻越大 (本次 8 KB × 303 ≈
   2.5 MB)。若要支持"单条几十 MB 的粘贴", 需要给窗口补字节上限 (本次未改代码)。
3. **Windows 侧没有堆归还**: 批量写入/压缩轮留下的空闲页会一直算在 RSS 里 (Linux 有
   `malloc_trim`); 是否加 `_heapmin` / `SetProcessWorkingSetSize` 需要单独评估
   (会影响每轮耗时)。这是 GB 级历史下 RSS 仍在 50 MB 上方 3~5 MB 的主要可回收项。
