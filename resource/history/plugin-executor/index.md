# 插件独立线程（插件执行器）

## 目标

让**插件代码永不运行在主程序的 io / UI 线程上**：所有"主程序调插件"的回调都投递到插件
自己的执行器上执行，io 线程只做受理、投递与状态机推进。

- 现状只是"约定"：回调里不许阻塞；一旦有插件违约，卡住的是整个 agent（模型流、其它会话、
  工具调度全停）。目标把它变成结构性保证。
- 插件因此拿到"单线程"心智模型（和 JS 脚本一样）：自己的状态不需要锁，回调之间不会并发。
- 与"接口表异步化"互补：异步化解决**插件 → 主程序**方向，本任务解决**主程序 → 插件**方向。

## 方案

见 [plan.md](plan.md)。要点：

- 每个插件管理器（agent 侧 `PluginManager`、client 侧 `ClientPluginManager`）各有一条
  **插件线程**，所有插件的回调与入口都在它上面串行执行；
- 框架侧 `PluginRuntime` 从"一个 executor"变成"**io 执行器 + 插件执行器**"两个，
  回调派发走插件执行器（复用现有 `enqueueRuntimeAction` + 实例 lease）；
- 实例可以**声明自带执行器**：JS 引擎插件把它已有的 JS 线程交出来，框架直接投递过去，
  不再多一跳；
- 生命周期（`start` / `stop` / `mount` / `unmount`）同样搬上去，`stop` 严格排在所有已派发
  回调之后；卸载超时按 `CloseFailed` 处理并**不卸载动态库**；
- 完成后 `scheduler.is_io_thread`、`ioCallSync` 这些"因为要跨线程"才存在的机制可以彻底删掉。

## 范围

做:
- 框架 `PluginRuntime` / `PluginHostCore` / `OpCore` 的双执行器改造与派发入口；
- 全部回调派发点改造（工具、图节点、能力行、生命周期、通道事件、后台任务事件、广播订阅、
  client 的动作/定时器/快捷键/渲染器/命令）；
- agent 侧与 client 侧各一条插件线程，以及线程清单、命名与日志标识；
- 实例自带执行器的声明接口（JS 引擎用）；
- 回调耗时预算与观测指标（`dev_mode`）；
- 文档：`plugins.md` 的线程模型一节、`AGENTS.md` 的线程清单。

不做:
- 不做"每插件一条线程"（先共享一条；需要时再按开关加）；
- 不把 io 线程拥有的状态（会话、注册表、图引擎）搬到插件线程 —— 它们仍归 io；
- 不做进程级共享执行器（agent 与 client 各自一份）；
- 不取消后台任务线程池（它承担 `offload` / 阻塞工具 / 文件与磁盘工作，与插件线程职责不同）。

## 状态

已实施（2026-11）。分阶段记录见 [work.md](work.md)，结论见下方“结论”。

前置: [plugin-api-async](../plugin-api-async/index.md)。接口表没异步化之前，把插件代码
搬到另一条线程只会让每次表调用变成一次"插件线程阻塞等 io"的往返，反而更慢；
异步化完成后这一步才划算。

## 关键决策

1. **一条插件线程，不是每插件一条**：与 JS 引擎的取舍一致（串行、省内存、作者不用锁）；
   代价是一个插件阻塞会拖住别的插件，用"每回调耗时预算 + 观测"兜住，需要时再加开关。
2. **两条执行器，不是把 io 让给插件**：io 执行器继续持有全部状态与定时器，插件执行器只跑
   插件代码。状态机不跨线程。
3. **实例自带执行器**：JS 引擎已经有 JS 线程，声明出来直接投递，避免"插件线程 → JS 线程"
   多一跳。
4. **卸载不硬等**：`stop` 与 drain 都有超时；超时记 `CloseFailed`、**不 `dlclose`**（宁可泄漏
   一个库，也不要让迟到回调落在已卸载的代码上）。
5. **顺序只按受理顺序**：同一实例的派发严格 FIFO；`stop` 排在已受理的全部回调之后，
   之后不再派发。

## 风险

- 单线程串行带来的队头阻塞：先用预算与指标观测，必要时提供每插件线程开关。
- 框架改动面大（`OpCore` 完成投递、生命周期 drain、全部派发点）：分阶段、每阶段可回归。
- 卸载路径变复杂：用现有 `InstanceLifetime` lease + 超时重试机制承担，`plugin_cleanup` 覆盖。

## 结论

**做了的**（agent 侧已默认生效；client 侧派发点已迁移、线程可选开启）:

1. `PluginRuntime` 从"一个 executor"变成两个: `executor` (io, 主程序状态) +
   `pluginExecutor` (插件代码)。`pluginExecutor` 为空 = 行为完全不变，测试与直接 new
   管理器的嵌入方不受影响 —— 这一条让"先落派发机制、再开线程"成为可能。
2. 唯一的派发入口 `pluginxx::dispatchToPlugin(inst, label, fn, opts)`: 投到插件执行器，
   **取实例 lease 后**才进插件代码（拿不到就丢弃并计数）。因此"取消后不再进插件代码"
   与"dlclose 安全"是同一件事，卸载不再需要"边跑边卸"的兜底。
3. 派发覆盖全部"主程序 → 插件"方向: `OpCore` 的 start / cancel / 完成回调、生命周期
   四个入口、驱动票、能力链、广播订阅、`sleep`/`offload` 完成回调、通道事件、
   后台任务事件、client 的动作/定时器/快捷键/渲染器/命令。io 线程只受理、投递、推状态机。
4. 可观测性: `PluginCallbackStats`（callbacks / 总耗时 / 最大 / 超预算 / dropped /
   unschedulable，预算固定为框架默认 100 ms，`setPluginCallbackBudget` 可改、暂无 yaml 键），
   写操作全无等待。
5. `scheduler.is_io_thread` 名字不变、语义变成"当前线程是不是该插件的执行线程"——
   kit 的同步桥与 `netCall` 一类阻塞助手用它做安全闸，没有 ABI 换代。

**偏差与预留**:

1. **不做实例自带执行器**（plan §5.4）: JS 引擎保持 "io → 插件线程 → JS 线程" 三跳。它
   自己的同步桥 (`tableOpSyncWait`) 必须跑在**不是**插件执行线程的线程上，声明自带执行器
   反而会与同步桥互等。框架留了判定入口，留给将来"自带 asio 执行器且不用同步桥"的插件。
2. **client 侧插件线程默认不启动**: 派发点已全部迁移，但内置 client 插件的 `start`/`stop`
   还在用同步表助手登记注册（插件线程上会被拒绝: 完成回调要投回这条线程，而它正阻塞）。
   开关是 `ClientPluginManager::startPluginThread()`，前置条件写在该函数注释与
   plugins.md §15.3；把那些注册事务改成异步形态后才能默认打开。
3. **不删 `is_io_thread` / `ioCallSync`**: 前者语义改为"插件执行线程判定"后仍是 kit 同步桥
   的安全闸；后者在过渡期是"插件线程同步等 io"，卡住的只是插件自己，且只刺两处
   （`call_tool` 与 `mount` 入口）。要彻底删掉得把这两个入口改成纯异步。

**新增/改动的测试**: `plugin_executor` 模块（10 组: 派发线程与 FIFO / 租约与关闭后丢弃 /
预算 / OpCore 三处 / 生命周期入口 / 驱动票 / 广播处理器 / 执行器停止 / 真实
`AgentHost` 加载 `agentxx_javascript_engine` / 真实 DSO 的 JS 脚本工具端到端）。
全量回归 43792 项断言 0 失败。

**连带修的两处**: JS 引擎 `start` 的能力登记改成异步形态（否则有插件线程时它自己加载不起来）;
`plugin_runtime` 的 offload 用例改为按"派发项也持一份 lease"断言。
