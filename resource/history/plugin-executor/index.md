# 插件独立线程（插件执行器）

## 目标

让**插件代码永不运行在主程序的 io / UI 线程上**：所有"主程序调插件"的回调都投递到插件
自己的执行器上执行，io 线程只做受理、投递与状态机推进。

- 现状只是"约定"：回调里不许阻塞；一旦有插件违约，卡住的是整个 agent（模型流、其它会话、
  工具调度全停）。目标把它变成结构性保证。
- 插件因此拿到"单线程"心智模型（和 JS 脚本一样）：自己的状态不需要锁，回调之间不会并发。
- 与"接口表异步化"互补：异步化解决**插件 → 主程序**方向，本任务解决**主程序 → 插件**方向。

## 方案

见 [plan.md](plan.md)。要点：

- 每个插件管理器（agent 侧 `PluginManager`、client 侧 `ClientPluginManager`）各有一条
  **插件线程**，所有插件的回调与入口都在它上面串行执行；
- 框架侧 `PluginRuntime` 从"一个 executor"变成"**io 执行器 + 插件执行器**"两个，
  回调派发走插件执行器（复用现有 `enqueueRuntimeAction` + 实例 lease）；
- 实例可以**声明自带执行器**：JS 引擎插件把它已有的 JS 线程交出来，框架直接投递过去，
  不再多一跳；
- 生命周期（`start` / `stop` / `mount` / `unmount`）同样搬上去，`stop` 严格排在所有已派发
  回调之后；卸载超时按 `CloseFailed` 处理并**不卸载动态库**；
- 完成后 `scheduler.is_io_thread`、`ioCallSync` 这些"因为要跨线程"才存在的机制可以彻底删掉。

## 范围

做:
- 框架 `PluginRuntime` / `PluginHostCore` / `OpCore` 的双执行器改造与派发入口；
- 全部回调派发点改造（工具、图节点、能力行、生命周期、通道事件、后台任务事件、广播订阅、
  client 的动作/定时器/快捷键/渲染器/命令）；
- agent 侧与 client 侧各一条插件线程，以及线程清单、命名与日志标识；
- 实例自带执行器的声明接口（JS 引擎用）；
- 回调耗时预算与观测指标（`dev_mode`）；
- 文档：`plugins.md` 的线程模型一节、`AGENTS.md` 的线程清单。

不做:
- 不做"每插件一条线程"（先共享一条；需要时再按开关加）；
- 不把 io 线程拥有的状态（会话、注册表、图引擎）搬到插件线程 —— 它们仍归 io；
- 不做进程级共享执行器（agent 与 client 各自一份）；
- 不取消后台任务线程池（它承担 `offload` / 阻塞工具 / 文件与磁盘工作，与插件线程职责不同）。

## 状态

规划中（2026-11）。设计见 [plan.md](plan.md)，实施未开始。

异步化完成后这一步才划算（过渡期可以先做生命周期那一批，见 plan.md 阶段 A）。

## 关键决策

1. **一条插件线程，不是每插件一条**：与 JS 引擎的取舍一致（串行、省内存、作者不用锁）；
   代价是一个插件阻塞会拖住别的插件，用"每回调耗时预算 + 观测"兜住，需要时再加开关。
2. **两条执行器，不是把 io 让给插件**：io 执行器继续持有全部状态与定时器，插件执行器只跑
   插件代码。状态机不跨线程。
3. **实例自带执行器**：JS 引擎已经有 JS 线程，声明出来直接投递，避免"插件线程 → JS 线程"
   多一跳。
4. **卸载不硬等**：`stop` 与 drain 都有超时；超时记 `CloseFailed`、**不 `dlclose`**（宁可泄漏
   一个库，也不要让迟到回调落在已卸载的代码上）。
5. **顺序只按受理顺序**：同一实例的派发严格 FIFO；`stop` 排在已受理的全部回调之后，
   之后不再派发。

## 风险

- 单线程串行带来的队头阻塞：先用预算与指标观测，必要时提供每插件线程开关。
- 框架改动面大（`OpCore` 完成投递、生命周期 drain、全部派发点）：分阶段、每阶段可回归。
- 卸载路径变复杂：用现有 `InstanceLifetime` lease + 超时重试机制承担，`plugin_cleanup` 覆盖。
